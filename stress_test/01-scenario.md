# 01 · 测试场景

## 一次"测试用户 run"的完整流程

每个虚拟用户（Virtual User, VU）在一次 run 中**串行**走完下面的 11 步。多个 VU 之间**完全并行**。run 结束后该账户不再复用——下一次测试重新注册新账户。

```
┌──────────────────────────────────────────────────────────────────┐
│  虚拟用户 N（每次 run 都是全新身份，与其他 VU 完全隔离）              │
└──────────────────────────────────────────────────────────────────┘
            │
            ▼
   ┌─────────────────┐
   │ 1. 注册账户       │  随机生成 email + password
   └─────────────────┘
            │  access_token
            ▼
   ┌─────────────────┐
   │ 2. 创建 patient   │  随机生成 name（避免重名干扰）
   └─────────────────┘
            │  patient_id
            ▼
   ┌────────────────────────────────────────────┐
   │ 3. 上传 5 份文档（并发或串行均可，建议并发）     │
   │    上传时携带 patient_id —— 后端会自动归档     │
   └────────────────────────────────────────────┘
            │  doc_id × 5；上传时 OCR 已自动入队
            ▼
   ┌─────────────────────────────────────────┐
   │ 4. 等待 5 份文档 OCR 完成                 │
   │    轮询 POST /documents/statuses          │

   └─────────────────────────────────────────┘
            │
            ▼

   └─────────────────────────────────────────┘
            │
            ▼
   ┌─────────────────────────────────────────┐
   │ 6. 归档（无需调用，上传时已自动完成）         │
   │    —— 仅为流程完整性保留此步骤              │
   └─────────────────────────────────────────┘
            │
            ▼

            ▼

   │ 10. CRF 全量抽取                           │
   │    POST /projects/{pid}/patients/{ppid}/   │

   │    轮询 task_batches/{batch_id}            │
```

## 关于"5 ops/sec"的口径

业务流程是有依赖关系的链式调用，**不存在"每秒固定发 5 次请求"这种说法**。"5 ops/sec" 在本场景里翻译成：

- 每个 VU **持续在飞**的请求数 ≈ 1（串行链路，前一步不完成下一步不开始）
- 真正"持续 5 ops"的是**轮询阶段**：第 4、5、7、10、11 步都有 1Hz~5Hz 轮询 batch / job 状态
- 因此"5 账号 × 5 ops/sec = 25 并发"的实质是：
  - 5 VU 各自处于轮询阶段时，每秒共发出 ~25 次状态查询
  - 上传 / 触发抽取这些动作偶发，**不是稳态 QPS**

这决定了压测的真实负载形态：

```
时间 →
VU1: [上传爆发] [轮询轮询轮询...] [触发] [轮询...] [触发] [轮询...]
VU2: [上传爆发] [轮询轮询轮询...] [触发] [轮询...] [触发] [轮询...]
...
                ↑                                  ↑
            CPU/网络爆发                       LLM/TextIn 爆发
            (上传 5 份/账户)                  (异步抽取被消费时)
```

后端实际看到的是：**短峰值（上传/触发）+ 长平台（轮询 + 异步 worker）**，不是均匀 25 QPS。

## 单 run 估时（粗算）

按真实外部依赖（TextIn + LLM）的典型耗时估计：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| 1-2 注册 + 建 patient | < 1s | |
| 3 上传 5 份 | 2-10s | 取决于文档大小 + OSS 网络 |
| 4 等 OCR × 5 | 30-120s | TextIn 串行处理，每份 6-25s |
| 5 元数据 × 5 | 20-60s | LLM 调用 |
| 7 EHR 抽取 | 30-90s | 多字段 LLM |
| 8-9 建项目 + 入组 | < 2s | |
| 10 CRF 全量 | 60-180s | 字段多，LLM 调用密集 |
| 11 靶向抽取 | 10-30s | 只跑指定字段 |

**单 run 端到端 ≈ 3-8 分钟**。这意味着 5 个 VU 同时跑，**完成一轮全部 run 大约 3-8 分钟**，期间持续产生轮询 + 外部 API 调用的复合压力。

## 测试矩阵（建议运行顺序）

| # | 并发 VU 数 | 持续时间 | 目的 |
|---|---|---|---|
| 1 | **1** | 单跑 1 轮 | 冒烟：验证脚本能跑通 |
| 2 | 1 | 30 分钟 | 单账户基线：得到每步骤的 p50/p95 |
| 3 | 3 | 30 分钟 | 小并发：观察是否出现争用 |
| 4 | **5** | 60 分钟 | 目标负载：本期核心结论 |
| 5 | 10 | 30 分钟 | 探测：找到首个明显劣化点 |

## 一个 run "成功"的定义

VU 完整走完 11 步且：

- 任何一次 HTTP 调用 **不返回 5xx**
- 第 4 步所有 5 份文档 `ocr_status = completed`（不允许 failed）
- 第 5 步所有 `meta_status ∈ {completed, skipped}`
- 第 7、10、11 步 batch/job `status = succeeded`
- 端到端耗时 ≤ 10 分钟（超过判定为业务超时）

任何一条不满足，该 run 标记失败，但**不中断其他 VU**。失败统计在 04-metrics.md 里详细定义。
